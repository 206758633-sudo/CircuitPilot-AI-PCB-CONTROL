## 0. 使用说明与 Lead 仲裁

### 0.1 判定符号

| 符号 | 含义 |
| --- | --- |
| ❌ FAIL | 已用图像/文档证据确认违反硬门禁 → 阻断投产 |
| ⚠️ 待复核 | 图像无法判定，必须在 EDA / 板厂 / 网表 / 实物上复核（不复核 = 不得放行） |
| ✅ PASS | 已确认满足 |

> **铁律：⚠️ 不等于 ✅。** 任何一条 ⚠️ 未闭合，都不得进入投板。

### 0.2 Lead 仲裁（4 项争议的最终口径）

| # | 争议 | 仲裁结论 |

| DFA | 1:1 打印 + 3D 视线检查；测试点单独建 `TP` 层 | 治具可及性必须实物验证 |
| GATE | 五道门禁的输出物归档，作为放行证据 | 建议纳入版本管理 |

### 5.1 自动化执行（推荐替代人肉打勾）

本清单的 151 条规则已被 `runtime/engineering/layout-rules.mjs` 实现为可执行判定：

```bash
node --test runtime/engineering/layout-rules.test.mjs   # 引擎自测（含"现状板缺陷逐条命中"断言）
node --input-type=module -e "import('./runtime/engineering/layout-rules.mjs').then(async m=>{const f=await import('./runtime/engineering/rules/fixtures.mjs');console.log(m.evaluateLayoutRules(f.defectiveTestBoard()).summary)})"
```

- 现状板：`PASS 12 / FAIL 54（硬门禁 50）/ REVIEW 58 / NA 4`，`GATE-01`、`GATE-07` 不通过 → 与 §1.9 的人工统计（49 条违反、其中 45 条硬门禁）在同一量级；差异来自引擎对"方向类别/线缆禁布区/测试点"等条目一并判 FAIL，人工统计当时按"已确认"从严计数。
- 整改骨架：`FAIL 0 / 10 道门禁 PASS`，证明规则不是不可执行的教条。
- 完整输入/输出契约见 [`docs/implementation/pcba-layout-rules-integration.md`](../implementation/pcba-layout-rules-integration.md)。
- 编号不可重排、不可改格式（`前缀-两位序号`），否则会与 JSON、清单、图 A 标注三处失联。
