# 批量写 / 批量导出评估（2026-10-29）

> 结论：**批量只读校验可做且已真机跑通；批量写入和批量导出不能做“一次批准全部执行”。**  
> 每块板必须有独立计划、独立 `planHash`、独立人工确认和独立执行记录；导出还受生产人工门禁约束。

## 1. 已有能力

- `cp_validation{boards}`：最多 3 块板，顺序跑 ERC/DRC/门禁；单板失败不拖垮整批；目标级通过判定已修正（不能把“任务完成”当“板子通过”）。
- 真实 2 板只读批量：1 通过 / 1 失败（第二块 1 条 unexplained DRC），证据 `artifacts/agent-eda-batch-20261029.json`。

## 2. 批量写为什么不能复用“一个批准”

1. **计划绑定**：批准令牌绑定一个 `planHash` 和一个 target fingerprint/window；不可能用一个令牌覆盖多块板。
2. **目标漂移**：每块板的 active window/document/pcb uuid 都可能不同；逐板必须重新读 context、重新加写锁。
3. **故障爆炸半径**：一块板写失败/回滚失败时，不能让后续板继续写；必须停止整批并保留现场。
4. **审计**：每块板需要独立 execution、快照、DRC、rollback 记录，不能只留一条“批量成功”。
5. **人工确认**：用户必须看到每块板的 board/uuid/planHash/风险/操作类型，不能用一个“全部批准”替代逐板确认。

## 3. 可接受的批量写形态

- 批量 **plan 生成**：可为多块板生成候选计划（只读），逐板展示 `planHash`、缺失项、风险。
- 逐板 **approve + execute**：串行；每板执行前重新读 target fingerprint；任一板失败 → 停止后续板，已成功板保留记录。
- 每板独立 `requestId`、独立 approvalId、独立 execution；审计按板记录。
- 不做批量回滚承诺；回滚只对单板单次执行负责。

## 4. 批量导出

- 导出是执行类动作，受 `release-gate`/人工门禁约束：A16 工程分析、在线 DFM、工程师终审签核等必需项缺失时，Runtime 必须 block，不能因为“批量”而绕过。
- 可做批量 **导出预检**（只读）：逐板检查门禁 block 原因、证据完整性、是否有人工签核；结果只报告，不生成正式生产文件。
- 正式导出仍应逐板人工确认，并保留每板输出 manifest/哈希/证据。

## 5. 建议下一步

1. 先完成自动回滚真机复验（P0）。
2. 实现“批量计划生成 + 逐板人工确认”的只读/半自动流程；不实现一键批量写。
3. 批量导出只做预检；正式导出保持逐板门禁。
4. 若未来必须批量写，增加“批次编排器”串行执行、失败熔断、逐板审计，且每个写动作仍消费独立批准令牌。

## 6. 当前状态

- 批量只读：已真机验证并通过语义修复。
- 批量写：**未实现，不建议在当前安全模型下实现一键批准**。
- 批量导出：**未实现**；只可做逐板预检/人工门禁。
