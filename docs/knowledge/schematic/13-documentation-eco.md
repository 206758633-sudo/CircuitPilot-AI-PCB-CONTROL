# 文件与 ECO：版本矩阵、变更控制、BOM、评审门禁与归档

> **一句话结论**：硬件项目的“文件正确”不是某个文件正确，而是**原理图、BOM、PCB、固件、测试记录之间始终存在一张可核对、可回滚的版本矩阵**；ECO 是改变这张矩阵的唯一合法入口，任何绕过 ECO 的修改都是事故的起点。

## 适用范围与边界

| 项 | 内容 |
| --- | --- |
| 适用阶段 | 原理图/PCB 设计 → 打样 → 试产 → 量产 → 变更维护 |
| 输入 | 设计文件（原理图/BOM/PCB/固件）、变更需求、供应商 PCN、测试与认证记录、质量体系要求 |
| 输出 | 版本矩阵、ECO 记录、变更影响分析、BOM 变更与替代料评估、评审门禁记录、归档文件包 |
| 不覆盖 | 具体 PLM/ERP 系统实施、法务合同、具体认证标准条款；涉及标准原文与保留年限的必须查原文/问质量部门 |
| 编号说明 | 本篇知识点编号为 **KP-SCH-263～286**（延续全局连续编号） |

## 一、受控文件与版本矩阵

### KP-SCH-263 文档受控总则：唯一入口、唯一版本、可追溯

- **判据**：所有对外/对生产生效的设计文件必须处于受控状态：有唯一编号、版本、发布日期、批准人；受控文件只能通过 ECO 修改；现场/产线/外协只能使用受控版本；草稿/临时文件不得进入生产流程。
- **为什么**：硬件事故的常见根因不是设计错，而是“用了旧版 BOM/旧版 Gerber/旧版测试程序”；没有受控入口，版本就会在邮件/聊天/共享盘里分叉。
- **怎么做**：建立受控文件清单（文件编号、名称、版本、状态、存放位置、责任人）；生产/外协发放时记录版本与签收；草稿放在非受控区并标记“非生产用”；发布时生成 PDF/BOM/网表并计算内容哈希。
- **怎么查**：抽查产线/外协实际使用的文件版本与受控清单是否一致；检查文件头版本/日期/批准人；不通过 → 收回旧版、重新发放、追查影响范围。

### KP-SCH-264 版本矩阵：原理图/BOM/PCB/固件/测试五件套

- **判据**：项目必须维护一张版本矩阵，至少覆盖：原理图、BOM、PCB/Gerber、固件、测试程序/测试记录；每行给出当前版本、发布日期、批准人、关联 ECO 号；任一文件的版本变化必须更新矩阵；矩阵中必须能回答“某块板对应哪版固件/哪版测试程序”。
- **为什么**：同一块板可能原理图 v1.3、PCB v1.2、固件 v2.0，矩阵是唯一能快速判断“这组合是否验证过”的工具；没有矩阵，返修/客诉/换料时无法定位。
- **怎么做**：用表格维护，示例字段：文件类型 / 文件编号 / 版本 / 日期 / ECO / 批准人 / 关联测试记录；发布时同步更新；矩阵随文件包归档；在板卡标签/序列号系统中记录版本组合。
- **怎么查**：随机抽 2 块板，按序列号反查其版本组合与测试记录；核对矩阵与实际文件头；不通过 → 补矩阵/冻结发版。

### KP-SCH-265 版本号语义与递增规则

- **判据**：版本号必须定义语义并全项目统一：主版本用于拓扑/接口/关键器件/结构变更，次版本用于器件值、位号、丝印、非功能性调整（具体分级按公司规范）；每次发布必须递增，禁止覆盖旧版本；旧版本必须可检索/可回滚。
- **为什么**：语义不清会让“改了一颗电阻”和“换了电源拓扑”看起来一样，评审与验证强度无法匹配；覆盖旧版则失去回滚能力。
- **怎么做**：在项目规范里写清主/次版本定义与示例；版本号与 ECO 号绑定；发布时旧版本归档不删除；文件名含版本与日期。
- **怎么查**：抽查历史版本是否可追溯；核对变更内容与版本递增是否匹配；不通过 → 修正版本记录并补归档。

### KP-SCH-266 版本一致性校验：三件套/五件套对齐

- **判据**：发布前必须做一致性校验：原理图导出的网表 ↔ BOM ↔ PCB 网络表/位号表 ↔ 固件配置（引脚/外设/版本宏）↔ 测试程序；校验必须自动化或双人核对，并记录结果；任一项不一致不得发布。
- **为什么**：人工“看一眼”无法发现位号/网络/固件配置的细微差异；自动化 diff 能把“原理图加了 TVS、PCB 没加封装”这类问题在发布前拦住。
- **怎么做**：导出网表与 BOM 做位号/网络/数量比对；PCB 导出网络表与原理图网表比对；固件配置里的引脚映射与原理图核对；把校验脚本/报告纳入发布门禁；报告含时间、版本、差异清单。
- **怎么查**：复核校验报告；抽查 3 个网络/位号在三个文件中的一致性；不通过 → 修正后重跑校验。

### KP-SCH-267 文件命名、目录与元数据规范

- **判据**：受控文件必须有统一命名：`项目_板卡_文件类型_版本_日期`（或公司规定格式）；目录按项目/阶段/文件类型组织；文件属性（标题、作者、版本、关键词）与受控清单一致；禁止“最终版/最终版2/真的最终版”式命名。
- **为什么**：命名混乱是版本分叉的温床；统一命名让检索、归档、比对自动化成为可能。
- **怎么做**：定义命名模板与目录结构；发布时由脚本/模板生成文件名；文件属性写入项目/版本/日期；旧文件移入归档目录并保留只读权限。
- **怎么查**：抽查文件名与受控清单；检查是否有非规范命名的生产文件；不通过 → 重命名/归档/更新清单。

### KP-SCH-268 归档、保留与可读性

- **判据**：每个发布版本必须归档完整文件包：原理图源文件+PDF、BOM、PCB 源文件+Gerber、装配图、测试程序/记录、ECO、认证文件；归档介质要可读（避免只存不可打开的旧格式）；保留年限按公司质量体系与法规要求执行（**具体年限需查体系文件/法规原文，不得凭记忆写**）。
- **为什么**：返修、客诉、认证复核、法规抽查都需要历史版本；归档不完整会导致“板子还在、文件没了”。
- **怎么做**：按版本建立归档目录；生成 SHA-256 清单并在归档记录中登记；定期做可读性抽检（打开/校验）；关键项目异地备份；归档权限只读。
- **怎么查**：随机抽一个历史版本，确认文件齐全、可打开、哈希匹配；不通过 → 补齐归档/修复介质。

## 二、ECO 与变更控制

### KP-SCH-269 ECO 流程与必填字段

- **判据**：任何影响受控文件的变更必须走 ECO；ECO 至少包含：ECO 编号、变更前/后版本、变更内容、变更原因、影响文件清单、影响分析、验证计划、批准人/日期、生效日期、关联 PCN/客诉/认证信息。
- **为什么**：ECO 是变更的唯一合法入口，也是追溯“为什么改、改了什么、验证了什么”的证据；字段缺失会导致变更无法评审或无法追溯。
- **怎么做**：用统一模板；小改（器件值/丝印）可用简化流程但必须记录；大改（拓扑/接口/关键器件/结构）必须完整评审；ECO 与版本矩阵、BOM、测试记录双向链接。
- **怎么查**：抽查 ECO 字段完整性；核对 ECO 与版本矩阵/文件版本；不通过 → 补记录/冻结变更。

### KP-SCH-270 ECO 触发条件：什么变更必须开 ECO

- **判据**：以下变更必须开 ECO（清单可按公司规范扩展）：原理图网络/器件/位号/参数变更；BOM 料号/供应商/替代料；PCB 叠层/布局/布线/丝印；结构件/连接器；固件与硬件接口相关配置；测试规范/判据；认证相关元件。纯文档错别字可不走 ECO，但必须记录。
- **为什么**：触发条件不清会导致“有人改了没说”，最终版本矩阵与实际不一致；把“小改”排除在流程外是常见漏洞。
- **怎么做**：把触发条件写进公司规范并培训；在 EDA/PLM 中设置变更检查点；对“紧急改板”设快速 ECO 通道但仍需批准与记录。
- **怎么查**：抽查近期修改记录与 ECO 是否对应；不通过 → 补 ECO 或追责。

### KP-SCH-271 PCN（供应商变更通知）处理

- **判据**：收到供应商 PCN 必须评估：变更类型（晶圆/封装/工艺/料号/产地）、影响器件参数（电气/热/可靠性/尺寸/引脚）、对原理图/BOM/认证的影响；评估结论必须记录（接受/拒绝/需验证）；涉及关键器件的 PCN 必须做小批验证后才能切换。
- **为什么**：PCN 可能带来参数漂移、引脚/封装变化、认证失效；不评估直接切换会造成批量问题。
- **怎么做**：建立 PCN 台账（器件/供应商/变更类型/日期/结论/验证）；关键器件（电源、MCU、RF、连接器、晶振）逐项评估；需要时做对比测试（参数/温升/EMC/可靠性）；切换走 ECO。
- **怎么查**：抽查 PCN 台账与 BOM 实际料号；核对验证记录；不通过 → 补评估/暂停切换。

### KP-SCH-272 BOM 变更管理与替代料

- **判据**：BOM 变更必须走 ECO；替代料必须做“可替代性评估”：电气参数（耐压/电流/精度/容差/温度系数）、封装/引脚、极性、认证/安规、供应链与成本；替代料必须写入 BOM 的 AVL（批准供应商清单）并注明替代关系；不得在生产中“随手换料”。
- **为什么**：参数看似相同的替代料可能在 ESR、饱和电流、温度特性、封装热阻上差异很大；未经评估的替代会导致批量失效或认证失效。
- **怎么做**：建立 AVL 与替代料评估表；关键参数逐项对比（datasheet 页码作为证据）；替代料做小批验证；BOM 中标注首选/替代；变更走 ECO 并更新版本矩阵。
- **怎么查**：抽查 BOM 中的替代料是否有评估记录；对比替代料关键参数；不通过 → 暂停使用/补评估。

### KP-SCH-273 替代料参数差异评估清单

- **判据**：替代料评估必须逐项确认：额定电压/电流/功率、精度/容差、温度系数/工作温度、ESR/ESL（电容）、饱和电流/直流电阻（电感）、Vf/Vr/结电容（二极管/TVS）、Rds(on)/Vgs(th)/Qg（MOS）、封装尺寸/焊盘/引脚、极性/方向、认证状态。任一项不满足即判不可替代。
- **为什么**：替代料的风险集中在“数据手册首页参数相同、细节不同”（如电容介质从 X7R 变 Y5V、电感饱和电流不足）；逐项对比是唯一可靠的判断方法。
- **怎么做**：用评估表逐项填“原器件值/替代值/是否满足/依据页码”；对关键项做实测（如电容偏压特性、电感饱和电流）；评估结论与验证记录归档。
- **怎么查**：抽查评估表与 datasheet；对关键替代料做实测复现；不通过 → 拒绝替代/换料号。

### KP-SCH-274 原理图—PCB—BOM 同步变更

- **判据**：一次变更涉及多个文件时，必须作为同一个 ECO 一起发布：原理图改网络/器件 → BOM 同步 → PCB 同步（封装/布局/网络表）→ 测试程序/固件配置按需同步；任何文件滞后都视为未完成变更。
- **为什么**：分开发布会让中间状态被误用（如原理图加了器件但 PCB 没加封装，产线照旧 BOM 贴片）；同步发布是保证版本矩阵一致的前提。
- **怎么做**：ECO 中列全影响文件；变更后重新导出网表/BOM/Gerber 并做一致性校验（KP-SCH-266）；同步更新版本矩阵；发布包一次性归档。
- **怎么查**：抽查 ECO 的影响文件是否全部更新；做网表/BOM/PCB 比对；不通过 → 补齐同步后重新发布。

### KP-SCH-275 变更影响分析：接口/电源/认证/供应链

- **判据**：每个 ECO 必须做影响分析，至少覆盖：电气接口（电平/时序/阻抗）、电源（电流/时序/去耦）、热（功耗/温升）、EMC/认证（是否影响已认证项目）、结构（尺寸/装配）、固件（引脚/配置）、供应链（交期/成本/替代）。分析结论必须可执行（需要哪些验证）。
- **为什么**：变更的影响往往跨领域（如换一颗 LDO 可能影响热、时序、认证），只改一个文件不做分析会在后续阶段暴露。
- **怎么做**：用影响分析模板逐项打勾；对“影响认证”的变更必须评估是否需要重新认证（按认证机构要求）；对“影响固件”的变更同步固件版本；验证计划与 ECO 一起批准。
- **怎么查**：抽查 ECO 的影响分析与实际验证记录是否对应；不通过 → 补分析/补验证。

### KP-SCH-276 固件版本与硬件版本绑定

- **判据**：固件必须能识别/适配硬件版本：启动时读取硬件版本（GPIO/EEPROM/电阻编码）或至少在生产时绑定；固件版本与硬件版本的兼容矩阵必须记录；硬件变更导致引脚/外设变化时，固件必须同步升级并做回归。
- **为什么**：同一固件跑在不同硬件版本上可能出现引脚冲突/外设不存在/时序不符；没有绑定会导致“升级固件后旧板不工作”。
- **怎么做**：硬件版本编码（电阻/EEPROM/GPIO 组合）；固件启动校验并记录；发布时更新兼容矩阵；产线烧录时写入硬件版本与固件版本；变更走 ECO。
- **怎么查**：抽查不同硬件版本+固件组合的功能测试；核对兼容矩阵；不通过 → 补版本识别/限制升级。

### KP-SCH-277 测试记录与证据归档

- **判据**：每个发布版本必须有对应测试记录：测试项目、条件（温度/电压/负载）、判据、结果、设备与校准信息、测试人/日期；关键测试（安规/EMC/可靠性）必须有报告；测试记录与版本矩阵关联，缺记录视为未验证。
- **为什么**：没有记录的测试无法证明版本可用；认证/客诉/返修时需要证据链。
- **怎么做**：用统一测试模板；原始数据（波形/日志/截图）与报告一起归档；设备校准证书在有效期内；测试记录编号与版本/ECO 关联；失败项记录整改与复测。
- **怎么查**：随机抽版本查测试记录完整性；按记录复现关键测试；不通过 → 补测/补记录。

### KP-SCH-278 变更通知与发布：内部/外协/客户

- **判据**：变更生效前必须通知受影响方：内部（生产/测试/采购/品质）、外协（贴片/组装/测试）、客户（如涉及交付规格/接口/认证）；通知内容含变更点、生效批次/日期、旧版处理方式；客户变更按合同/质量协议执行。
- **为什么**：未通知的变更会导致产线用旧文件、外协贴错料、客户收到不一致产品；通知是变更闭环的一部分。
- **怎么做**：建立通知清单与签收记录；明确生效批次（按序列号/日期）；旧版文件回收/作废；客户变更走 PCN/ECN 流程（按合同）。
- **怎么查**：抽查通知签收与生效批次；核对产线/外协实际使用版本；不通过 → 补通知/隔离旧版。

### KP-SCH-279 量产文件包：Gerber/BOM/CPL/装配图/测试规范

- **判据**：量产文件包必须完整且版本一致：Gerber（含钻孔/叠层/阻抗报告）、BOM（含 MPN/位号/替代料/贴装状态）、CPL（坐标/角度/面）、装配图/丝印图、测试规范/治具说明、包装/标签要求；文件包必须与版本矩阵对应并归档。
- **为什么**：缺任何一个文件都会导致产线停线或做错；版本不一致会导致贴错/焊错。
- **怎么做**：用发布检查表逐项确认；Gerber 用 Gerber 查看器复核（层数/钻孔/外形）；BOM/CPL 与 PCB 位号比对；文件包生成哈希并归档。
- **怎么查**：按检查表逐项核对；让产线/外协试读文件包；不通过 → 补齐后重新发布。

## 三、门禁、追溯与审计

### KP-SCH-280 评审门禁与签核

- **判据**：发布前必须通过评审门禁：原理图评审、PCB 评审、BOM/选型评审、测试评审、变更评审（ECO）；每个门禁有明确的检查项、通过标准、签核人；阻断项未关闭不得发布。
- **为什么**：门禁把“个人经验”变成“组织能力”；没有签核的发布无法追责，也无法保证检查被执行。
- **怎么做**：定义门禁清单与角色（设计/评审/批准）；用检查表逐项打勾并留证；阻断项进问题单跟踪关闭；签核记录与版本绑定。
- **怎么查**：抽查签核记录与问题单关闭状态；不通过 → 补评审/暂停发布。

### KP-SCH-281 需求—设计—测试—认证的可追溯性

- **判据**：关键需求必须能追溯到设计实现与测试证据（需求 ID → 原理图网络/器件 → 测试项 → 结果）；认证相关项必须能追溯到认证报告；追溯链断裂视为未验证。
- **为什么**：追溯链是质量体系与客诉分析的基础；断裂时无法证明“这个需求被满足”。
- **怎么做**：给需求编号并在原理图/测试规范中引用；维护追溯矩阵；变更时更新追溯链；认证项单独标注。
- **怎么查**：抽查 3 条需求的追溯链是否完整；不通过 → 补链/补测试。

### KP-SCH-282 配置管理工具、权限与只读归档

- **判据**：受控文件应存放在配置管理系统（PLM/版本库/受控共享盘）中，具备版本历史、权限控制、签入/签出、审计日志；发布版本设为只读；删除/覆盖受控文件必须留痕。
- **为什么**：共享盘里的“可随意覆盖”是版本事故的根源；权限与审计日志能回答“谁在什么时候改了什么”。
- **怎么做**：定义目录权限（设计可写、生产只读）；启用版本历史与审计；发布时打标签/基线；离职/转岗时回收权限；定期备份。
- **怎么查**：抽查权限设置与审计日志；尝试覆盖受控文件应被拒绝；不通过 → 调整权限/补日志。

### KP-SCH-283 变更后验证与回归

- **判据**：变更后必须按影响分析执行验证与回归：受影响功能全测、关键指标复测、与其他版本的兼容性测试；回归范围不能只测“改的那一点”；验证通过才能生效。
- **为什么**：变更可能引入副作用（如换电容影响环路、改布局影响 EMC）；只测改动点会漏掉回归问题。
- **怎么做**：按影响分析列回归清单；覆盖电性能/热/EMC/可靠性/固件兼容；记录测试条件与结果；失败则回退或整改后重测。
- **怎么查**：核对回归清单与实际记录；抽查未覆盖项；不通过 → 补测/暂停生效。

### KP-SCH-284 版本回滚与冻结

- **判据**：必须定义回滚条件与回滚包：当变更导致批量问题/认证失败/产线停线时，能快速回到上一个受控版本；回滚包必须完整（文件+测试记录+固件）；冻结版本在冻结期内不得修改，除非走紧急 ECO。
- **为什么**：没有回滚能力时，一次坏变更会导致长时间停线；冻结能保证量产期间的稳定性。
- **怎么做**：保留上一个稳定版本的完整归档；回滚流程与责任人明确；回滚后更新版本矩阵与通知；冻结期与解冻条件写进项目计划。
- **怎么查**：演练一次回滚（文件/固件/测试）；核对冻结记录；不通过 → 补回滚包/流程。

### KP-SCH-285 认证与合规文件的版本管理

- **判据**：认证/合规文件（测试报告、证书、DoC、安规报告）必须与产品版本绑定；变更涉及认证相关元件/结构/固件时，必须评估是否触发重新认证；认证文件归档并与版本矩阵关联；**具体认证要求与有效期按对应标准/认证机构规定执行，不得凭记忆引用条款**。
- **为什么**：认证是按版本/配置发的，变更后未评估会导致证书失效；客户/海关/监管抽查时需要可追溯的认证文件。
- **怎么做**：建立认证台账（证书号/版本/有效期/覆盖型号）；变更影响分析包含认证影响；需要重认证时提前排期；认证文件与产品版本一起归档。
- **怎么查**：抽查认证台账与产品版本；核对变更是否触发重认证评估；不通过 → 补评估/更新证书。

### KP-SCH-286 文档审计、抽查与评审清单

- **判据**：定期做文档审计：抽查版本矩阵、ECO、BOM、测试记录、归档的一致性；审计发现问题必须整改并跟踪关闭；审计记录归档。
- **为什么**：文档体系会随时间腐化（临时改动、人员流动、系统迁移），定期审计能提前发现断链。
- **怎么做**：每季度/每项目节点抽查；用统一审计表；问题单跟踪；把审计结果纳入项目复盘。
- **怎么查**：按审计表逐项核对；抽查 3 个历史版本做端到端追溯；不通过 → 整改并复评。

| 类别 | 检查项 | 关键判据 | 证据 |
| --- | --- | --- | --- |
