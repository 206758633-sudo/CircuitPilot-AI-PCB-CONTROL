## Context

当前 React Demo 已有三类分散信息：`AuditEvent` 记录粗粒度业务事件、`CommandLog` 记录 EDA 类型化命令、局部组件通过 Toast 或 `task.error` 展示错误。它们无法表达字段级前后差异，也无法持续聚合、分派和关闭问题。修改日志与问题中心会同时影响领域类型、Reducer、持久化、跨页面事件写入、版本与审计页面、全局状态显示和自动化测试。

本变更继续遵守现有安全约束：全部外部操作为 Demo 模拟；问题文本不能成为可执行代码；错误详情不得包含密钥、任意文件内容或模型思维链。

## Goals / Non-Goals

**Goals:**

- 明确区分“审计事件”“工程修改”“问题报错”三种记录。
- 让用户集中查看每项修改的对象、字段、前值、后值、原因、证据和关联版本。
- 让用户集中查看、筛选、定位、重试、解决或带原因忽略问题。
- 让未解决问题在侧边导航和顶部状态区域持续可见。
- 无损迁移现有 Schema v1 本地 Demo 数据到 Schema v2。
- 保持所有动作可自动化验证且不引入真实外部服务。

**Non-Goals:**

- 不实现云端日志服务、多用户指派、邮件/即时消息告警或长期遥测。
- 不收集真实嘉立创EDA崩溃转储、系统隐私数据或模型内部推理。
- 不允许从报错文本执行任意脚本，也不自动修改真实电路板工程。
- 不把现有审计日志删除或强行转换成字段级修改记录。

## Decisions

### 1. 保留一个“版本与审计”主导航，在页面内增加四个清晰视图

页面将提供“版本时间线 / 修改日志 / 问题中心 / 审计日志”四个标签。侧边导航文字调整为“版本、日志与问题”，并显示未解决问题数字徽标；顶部状态总线增加可点击的 `ISSUES` 状态。

选择这一方案是因为版本、修改、问题和审计共同回答工程可追溯性问题，复用现有页面可以避免第九个主导航导致桌面侧栏过密。替代方案是新建独立错误页面，但它会割裂版本和错误上下文，也增加导航复杂度。

### 2. 新增两种领域实体，不复用 AuditEvent

新增 `ChangeLogEntry` 和 `IssueRecord`：

- `ChangeLogEntry` 保存来源、操作者、动作、对象、字段差异、原因及任务/计划/快照/版本/验证关联。
- `IssueRecord` 保存来源、严重度、状态、错误码、安全详情、发生次数、关系上下文、推荐动作和处理历史。

`AuditEvent` 继续记录“发生了一个业务事件”，`CommandLog` 继续记录命令请求/响应。这样避免把审计描述硬解析成差异，也避免把成功审计误当问题。详情视图通过关系 ID 关联三类记录。

### 3. 由 AppContext 暴露显式记录 API，并对重复问题做指纹聚合

AppContext 增加 `recordChange()`、`reportIssue()` 和 `updateIssue()`。各业务模块在完成语义明确的状态变更时显式调用，而不是让 Reducer 对所有 Action 做不可靠的通用深度 diff。

问题指纹采用 `source + code + primaryObjectId + taskId/command`。同指纹的未解决问题再次出现时更新 `lastOccurredAt` 和 `occurrences`；已经解决的问题复发时重新打开并追加处理历史。相比每次都新增行，这能降低重复噪声，同时保留频次信息。

### 4. 运行时 logger 使用受控 sink，问题内容经过安全化

现有 logger 保留控制台输出，并支持注册一个问题 sink。`warn`/`error` 仅把 `safeError` 允许的名称、消息、模块和有限元数据传给 `reportIssue()`；字段名命中 token、key、secret、authorization 时替换为 `[REDACTED]`。ErrorBoundary 仍显示致命错误，同时通过 logger sink 尝试持久记录。

替代方案是拦截所有 `console.error`，但第三方库噪声和不可控对象太多，因此不采用。

### 5. 问题动作必须映射到注册的类型化处理器

问题记录只保存 `recoveryAction` 枚举，例如 `retry-ai-task`、`reconnect-eda`、`rerun-validation`、`open-settings`、`create-ai-fix`。问题中心根据枚举调用现有受控业务动作或导航；不会运行错误文本中的代码或命令。

解决、忽略和重新打开会追加 `IssueHandlingEvent`，原始问题不会被删除。忽略必须填写原因，解决必须填写处置说明。

### 6. 使用双键读取完成 Schema v1 到 v2 的无损迁移

新的存储键为 `circuitpilot-demo-state-v2`。启动时优先读取 v2；若不存在则读取旧的 `circuitpilot-demo-state-v1`，验证核心数组后保留原数据，补充 `schemaVersion: 2`、种子修改日志和由现有失败/警告生成的初始问题。成功持久化 v2 后保留旧键一段演示周期，便于回退；确认重置时同时清理两个键并加载 v2 种子。

直接在旧键原地覆盖虽然更简单，但发生迁移错误时难以回滚，因此不采用。

### 7. 本地保留策略和导出边界

修改日志保留最新 500 条，问题保留最新 300 条，审计继续保留最新 200 条。诊断包包含安全化问题、EDA 命令和验证状态；工程评审包额外包含修改日志、关系 ID 和版本摘要。所有下载继续标记 `DEMO ONLY`。

## Risks / Trade-offs

- [显式记录 API 可能漏记某个新动作] → 为受控 Action 建立测试矩阵，并在新增业务功能的验收标准中要求 change/issue 事件断言。
- [Schema v1 数据字段可能不完整] → 迁移只依赖已验证的核心字段，缺失新增字段使用 v2 默认值，并记录持久化问题。
- [问题聚合可能合并不应合并的事件] → 指纹包含来源、错误码、主对象和任务/命令；详情保留 occurrence 历史。
- [全局错误徽标造成告警疲劳] → 仅统计 open/investigating，ignored/resolved 不计入；颜色取最高未解决严重度。
- [日志增长影响 LocalStorage] → 使用 500/300/200 上限并只保存安全、紧凑的结构化数据，不存附件或堆栈全文。

## Migration Plan

1. 增加 v2 类型、种子数据、纯迁移函数和单元测试。
2. 扩展 Reducer 与 AppContext 记录 API，在不改变现有页面行为的前提下接入事件源。
3. 实现修改日志、问题中心、详情与全局指示器。
4. 扩展 Demo 下载和 Playwright 交互测试。
5. 启动时优先加载 v2，验证 v1 迁移与损坏状态回退。
6. 若回归失败，可回退代码并继续使用未被覆盖的 v1 存储键。

## Open Questions

- 当前 Demo 暂定由本机单一操作者使用，actor 显示“用户”或“AI · Demo”；未来真实桌面版再接入账号身份。
- 当前不增加桌面系统通知；若后续需要后台运行与高严重度通知，应作为独立权限和隐私变更处理。
